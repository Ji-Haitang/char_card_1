# 项目向量召回功能说明

本文档说明"瀚海归义录"项目中，`emb_`（L0 向量）和 `wevt_`（L2 向量）两类向量在每轮 LLM 交互时的完整召回事件流与处理逻辑。

---

## 一、两类向量的定义与数据来源

### L0 向量（`emb_` 前缀）

| 属性 | 说明 |
|------|------|
| **对应数据** | `summaryHistory`——每轮 AI 回复中 LLM 自动生成的逐轮摘要（`summaryText`） |
| **向量化文本** | `地点：xxx\n在场NPC：xxx\n` + summaryText + `\n地点：xxx\n在场NPC：xxx\n`（前缀在头尾各重复一次，强化地点/NPC 在向量空间中的权重，改善位置相关的召回精度） |
| **存储 key** | IndexedDB 中格式为 `emb_<summaryId>` |
| **内存缓存** | `memoryRecall._cache`（Float32Array 列表） |
| **写入时机** | 每轮提交阶段结束后，fire-and-forget 异步写入 |
| **语义粒度** | 单轮叙事摘要，颗粒较细 |

### L2 向量（`wevt_` 前缀）

| 属性 | 说明 |
|------|------|
| **对应数据** | `eventHistory`——由 `eventRunner` 异步抽取的结构化剧情事件 |
| **向量化文本** | `地点：xxx\n在场NPC：xxx\n[timeLabel] description`（`buildEventEmbedText` 构造） |
| **存储 key** | IndexedDB 中格式为 `wevt_<eventId>` |
| **内存缓存** | `memoryRecall._cacheL2`（与 L0 完全分开） |
| **写入时机** | 每轮提交后异步触发 `eventRunner.maybeSchedule()`，满足滑动窗口步长后批量抽取并写入 |
| **语义粒度** | 跨多楼的叙事线骨架（一个完整事件含 title/description/npc/location/causedBy 等结构） |

两层向量的**向量化格式对齐**（均使用地点/NPC前缀），使 L0 摘要与 L2 事件落在同一语义空间，可直接用同一 query 向量跨层检索。

---

## 二、召回触发的整体时序

每次用户点击"发送"，`pipeline.runTurn()` 按如下顺序执行：

```
用户发送
  │
  ├─ Phase 0：预同步（一致性修复）
  │     ├─ _syncEmbeddingsWithSummaryHistory()   ← 修复 emb_ ↔ summaryHistory
  │     └─ _syncL2EmbeddingsWithEventHistory()   ← 修复 wevt_ ↔ eventHistory
  │
  ├─ Phase 1：构建双路查询向量
  │     ├─ Q_intent  = f(当前用户输入)
  │     ├─ Q_context = f(上一轮 AI 回复 + 地点/NPC前缀)
  │     └─ 批量 embed → [intentVec, contextVec]
  │
  ├─ Phase 2：L0 召回（summaryHistory 摘要层）
  │     └─ memoryRecall.recallRelevantMemories() → recalledMemories[]
  │
  ├─ Phase 3：L2 召回（eventHistory 事件层）
  │     ├─ memoryRecall.recallL2Events()          → 粗排候选[]
  │     ├─ 分流：实体强命中（免精排）∪ 普通候选（reranker 精排）
  │     ├─ memoryRecall.traceCausation()          → 因果前因[]
  │     └─ 挂载 L0 证据 → recalledEvents{ direct, prior }
  │
  ├─ Phase 4：注入 Prompt
  │     └─ promptBuilder.buildMessages() → <RecalledEvents> + <RecalledMemories>
  │
  ├─ LLM API 调用（流式/非流式）
  │
  └─ Phase 5：提交阶段更新索引（fire-and-forget）
        ├─ 新 summaryHistory → embed → 存 emb_ → 更新 _cache
        └─ eventRunner.maybeSchedule() → runEventSum() → 存 wevt_ → 更新 _cacheL2
```

---

## 三、详细处理逻辑

### Phase 0：预同步（一致性修复）

在发起任何召回前，pipeline 先做两路数据修复，确保缓存与持久化存储不脱节：

**`_syncEmbeddingsWithSummaryHistory()`（L0 同步）**
1. 加载全部 `summaryHistory` 和 `emb_` 记录
2. `emb_` 中存在但 `summaryHistory` 无对应 id → **删除孤立向量**，同步清出内存缓存
3. `summaryHistory` 有记录但缺对应 `emb_` → **补生成 embedding**，使用 `_buildEmbedText` 构造向量化文本（地点/NPC前缀 + summaryText），写入 IDB 并加入内存缓存

**`_syncL2EmbeddingsWithEventHistory()`（L2 同步）**
1. 逻辑与 L0 同步对称，但操作 `eventHistory` 和 `wevt_` 记录
2. 孤立 `wevt_` 先删（删孤优先于补建，保证事件号复用安全）
3. 缺失 `wevt_` 的事件调用 `buildEventEmbedText` 补生成向量

---

### Phase 1：构建双路查询向量

召回走**双路 RRF 架构**，每次召回同时使用两个查询向量，增强召回的鲁棒性：

#### Q_intent（意图路，权重基准 0.6）
- 来源：**当前用户输入**
- 处理（`_buildQueryIntentText`）：
  - 丢弃 `时间：` / `季节：` 开头的行（时间信息对语义召回无效）
  - 地点字段统一归一化为 `地点：xxx`
  - NPC 字段保留原 key 名和值
  - 其余行（行动选择/互动内容）原样保留

#### Q_context（上下文路，权重基准 0.4）
- 来源：**上一轮 AI 回复原文** + 上上轮用户消息中提取的地点/NPC前缀
- 用于召回与上一轮剧情连续相关的历史记忆

#### 向量化与 focusCharacters
- 两路文本**批量一次**调用 `embeddingService.embed()`（BAAI/bge-m3 模型），得到 `[intentVec, contextVec]`
- 同时扫描 intent + context 文本，与 `npcNameToId` 匹配，提取 **focusCharacters**（焦点NPC名列表），用于后续实体软过滤

---

### Phase 2：L0 召回（summaryHistory 摘要层）

调用 `memoryRecall.recallRelevantMemories(intentVec, contextVec, ...)`，步骤如下：

#### ① 排除 RecentMemories
- 近期摘要（`week >= 最后一条周总结.markWeek - 1`）已在当前 prompt 的 `<RecentMemories>` 滑动窗口内直接注入，**排除出召回候选池**，避免重复
- 排除 id 以 `excludeSet` 形式传入

#### ② 双路相似度计算
对 `_cache` 中每条记录（跳过 fingerprint 不匹配的旧向量）分别计算：
- `simIntent = cosine(intentVec, record.vector)`
- `simContext = cosine(contextVec, record.vector)`（若有）

#### ③ 加权 RRF 融合
两路分别按相似度降序排名后：

$$\text{rrfScore}(d) = \frac{w_{\text{intent}}}{K + \text{rank}_{\text{intent}}(d)} + \frac{w_{\text{context}}}{K + \text{rank}_{\text{context}}(d)}$$

- $K = 15$（RRF 平滑常数）
- $w_{\text{intent}} = 0.6 \times \text{lengthFactor}(\text{intentLen})$
- $w_{\text{context}} = 0.4 \times \text{lengthFactor}(\text{contextLen})$
- **长度因子**：输入字数 ≥100 → 1.0；字数 ≤0 → 0.35；线性插值。输入过短时压低对应路权重，防止泛化噪声顶入候选

#### ④ 阈值过滤 + 实体软过滤
- **最低阈值**：两路相似度取大值（max），`< 0.60` 直接丢弃
- **实体软过滤**：max sim `< 0.72` 时，候选文本须包含任一 focusNPC 名（OR 逻辑），否则丢弃
- 两规则互补：高置信度（≥0.72）的语义命中绕开实体检查；低置信度时须有实体锚点支撑

#### ⑤ Reranker 精排
取通过④过滤后的前 **20 条**候选（RERANK_CANDIDATE_LIMIT），送入 `reranker.rerankEvents()`：
- 模型：`BAAI/bge-reranker-v2-m3`（交叉编码器）
- query：`Q_intent + Q_context 前 500 字`
- 过滤：`rerankScore < 0.10` 的条目丢弃
- 失败/超时 → fallback 回 RRF 排序，不阻断主流程
- 精排后结果替换 `scored` 数组，进入下一步截断

#### ⑥ 双重截断
- 按精排分（或 rrfScore）降序取前 **topK=10** 条
- 同时累计 token 估算（中文 1字≈1token，英文 4字符≈1token），超过 **maxTokens=3000** 截断

---

### Phase 3：L2 召回（eventHistory 事件层）

#### ① 确定排除集合
- `week >= _recentThreshold` 的近期事件（已在上下文窗口内）排除
- 兜底：`week=0` 的老存档事件，若 `uiEnd >= uiConv.length - 40` 也视为近期排除

#### ② 粗排（双路 RRF）
调用 `memoryRecall.recallL2Events(intentVec, contextVec, opts)`：
- 在 `_cacheL2` 上执行与 L0 完全对称的双路 RRF 流程
- 参数：`candidateLimit=30`，`minSim=0.60`，相同的实体软过滤逻辑
- 返回按 rrfScore 降序的候选列表（**不做 token 截断**，待 reranker 精排后再定夺）

#### ③ 候选分流
```
候选 []
  ├─ focusNPC 实体强命中（文本含 focusNPC 且 simMax >= 0.75）→ _mustKeep（免精排）
  ├─ 词法高置信旁路（entry.lexBypass === true）→ 按 rrfScore 降序，仅前 _LEX_MUSTKEEP_CAP=3 条 → _mustKeep（免精排）
  │                                             └─ 超出 3 条的部分 → 回落 _normal（仍正常送精排）
  └─ 其余普通候选 → 送 reranker 精排
```

> 阈值辨析：`recallL2Events` 内部的实体软过滤用的是 `ENTITY_BYPASS_SIM = 0.72`；这里 pipeline.js 对已召回候选做「是否免精排」的 mustKeep 判定，用的是 `ENTITY_BYPASS_SIM + 0.03 = 0.75`，比软过滤阈值更高一档，两者用途不同，不要混淆。

`_mustKeep` 对应"语义+实体"双重高置信命中 **或** "词法路精确专名命中中信号最强的一小部分"，两者任一满足即直接保留，不受精排 topN 配额压缩。

> **为什么词法旁路也要（部分）免精排**：reranker 的 query 是 `intentText + contextText 前 500 字` 拼接而成，intent 里的短专名信号（如用户显式点名某 NPC）在长 context 面前容易被交叉编码器的整体语义打分淹没——即便候选文本字面包含该专名，如果 context 主题与候选内容语义不贴合，也可能被精排刷出 Top 名单。词法路在粗排阶段已经用精确字符串匹配确认了专名命中。
>
> **为什么不是全部（最多 5 条）免精排，而是只取 `_LEX_MUSTKEEP_CAP=3`**：`LEXICAL_BYPASS_CAP=5`（见 6.7）的语义是"这些候选不该被向量/实体阈值提前淘汰"，不等于"这些候选都该无条件跳过精排"。如果 5 条全部免精排，会占满 DIRECT 总预算（≤7），精排（能做更细粒度语义相关性/多样性判断）反而只剩 1~2 个名额，容易让若干只是**顺带命中常见专名**（而非真正强相关）的事件挤占最终结果。因此在 pipeline.js 层再收紧一档：词法旁路候选按综合 `rrfScore`（已融合词法 + 双路稠密信号）降序排序，只把信号最强的前 3 条视为高置信直接保留，其余仍送 `_normal` 正常参与精排——精排选不中也无妨，它们本就不是本轮最强证据，只是没有被过早淘汰的机会。

#### ④ Reranker 精排
调用 `reranker.rerankEvents(query, normalCandidates, { topN: 7 - mustKeep.length })`：
- 模型：`BAAI/bge-reranker-v2-m3`（交叉编码器，精度高于向量相似度）
- query：`Q_intent + Q_context 前 500 字`
- 返回 `rerankScore >= 0.10` 的 topN 条（DIRECT 总量上限 = mustKeep + reranked ≤ 7）
- 失败/超时 → fallback 回 RRF 粗排顺序（不阻断主流程）

#### ⑤ 合并 DIRECT 候选
`DIRECT = _mustKeep ∪ _reranked`（按 id 去重，mustKeep 在前）

#### ⑥ 挂载 L0 证据
对每条 DIRECT 事件，遍历 `recalledMemories`：若某 L0 摘要对应的 UI 消息 index（通过 `UIid → _idxMap`）落在事件的 `uiStart～uiEnd` 范围内，则作为该事件的 **L0 证据**挂载。

被挂载的 L0 条目标记为 `_usedL0`，从 `recalledMemories` 中移除（避免重复注入 prompt）。

#### ⑦ 因果链追溯
调用 `memoryRecall.traceCausation(directEvents, eventById)`：
- 沿每条直接命中事件的 `causedBy` 字段 BFS 向前追溯
- `maxDepth=4`（追四代前因），`maxAdd=20`（最多候选 20 条前因）
- 排序：被多条事件引用 + 深度浅的前因优先
- 追溯结果作为 `priorById`（字典形式，供 prompt-builder 内联渲染树形因果链；仅描述，不挂 L0）

#### ⑧ 输出
```js
recalledEvents = {
  direct:   [ { event, evidence: [{ week, text }] } ],  // 直接命中事件 + L0 证据
  priorById: { [id]: event, ... }                        // 因果前因字典（仅描述）
}
recalledMemories = recalledMemories.filter(孤儿 L0)     // 未被挂载的 L0 仍独立传递
```

**L2 token 上限**：DIRECT 事件逐条累计 token 估算，总量超过 **5000 token** 时触发降级——先尝试不带 L0 证据版本；若仍超限则停止追加后续事件（保证至少注入第一条）。

### Phase 4：注入 Prompt

`promptBuilder.buildMessages()` → `_buildHistorySummaryBlock()` 中构建 `<HistorySummary>` 块：

```
<HistorySummary>
  <PreviousMemories>      ← weekHistory 周总结（按 token 预算截断）
  </PreviousMemories>

  <RecalledEvents>        ← L2 直接命中事件（_buildRecalledEventsBlock）
    [第X年第M月第W周] 事件标题
    事件描述
      [证据]
      - L0 摘要证据文本
      ...

    <!-- prior causes traced via causedBy chain -->
    [第X年第M月第W周] 前因事件标题（前因）
    前因描述
  </RecalledEvents>

  <RecentMemories>        ← 近期 summaryHistory 滑动窗口（直接注入，不走召回）
  </RecentMemories>

  <RecalledMemories>      ← 孤儿 L0 向量召回摘要（未被 L2 挂载的）
  </RecalledMemories>
</HistorySummary>
```

`<RecalledEvents>` 为**主干记忆注入**，优先级最高；`<RecalledMemories>` 为补充细节。

---

### Phase 5：提交后更新索引（fire-and-forget）

LLM 回复成功提交后，异步触发两路索引更新：

#### L0 索引更新
1. 比对 `summaryHistoryService.getAll()` 与内存缓存 `stats.entries`，找出新增但尚未向量化的摘要
2. 批量调用 `embeddingService.embed(embedTexts)` 生成向量
3. `storageService.saveEmbedding(id, Float32Array, meta)` 写入 IDB
4. `memoryRecall.addToCache(record)` 更新内存缓存

#### L2 索引更新（eventRunner）
1. `eventRunner.maybeSchedule()` 异步触发（`setTimeout(..., 0)`）
2. **触发条件**：`uiConversation.length - watermark > eventStep`（默认 step=20，可动态增量）
3. `runEventSum()` 执行：
   - 从 watermark 取一个滑动窗口（最大 `2 × step` 条），提取 assistant 楼层，打局部序号
   - 回灌历史事件（causedBy 引用锚点）+ 加载 eventMeta 基线（弧光+事实，按在场实体过滤）
   - 调用 LLM（复用 apiService，走 EVENT_SYSTEM_PROMPT），输出结构化 JSON
   - JSON 包含：`events[]`（新事件）、`arcUpdates[]`（角色弧光增量）、`factUpdates[]`（SPO 世界事实增量）
   - 局部序号 → total index 映射，写入 `eventHistoryService.appendEvents()`
   - 对每条新事件：`embeddingService.embed([buildEventEmbedText(ev)])` → `storageService.saveL2Embedding()` → `memoryRecall.addToCacheL2()`
   - `eventHistoryService.applyMetaUpdates()` 合并弧光/事实到 `eventMeta`
   - watermark 推进至 `lastAsstIdx`（最后一条 assistant 楼层的 total index）

## 四、关键参数速查

| 参数 | 值 | 说明 |
|------|----|------|
| L0 召回 topK | 10 | 最多返回 10 条摘要 |
| L0 maxTokens | 3000 | 召回部分 token 上限 |
| L0 Rerank 候选上限 | 20 | MIN_SIM 过滤后送入 Reranker 的最大条数 |
| L0 Reranker minScore | 0.10 | L0 精排最低分，低于此值丢弃 |
| L2 candidateLimit | 30 | 粗排候选上限 |
| L2 Reranker topN | `7 - mustKeep.length` | 精排保留上限（DIRECT 总量 ≤ 7）|
| L2 Reranker minScore | 0.10 | L2 精排最低分 |
| L2 token 上限 | 5000 | DIRECT 事件累计 token 上限，超限触发降级 |
| 因果链 maxDepth | 4 | 追溯层数 |
| 因果链 maxAdd | 20 | 前因候选上限 |
| MIN_SIM | 0.60 | L0/L2 共用的最低相似度阈值 |
| ENTITY_BYPASS_SIM | 0.72 | 实体软过滤绕行阈值 |
| RRF_K | 15 | RRF 平滑常数（L0/L2 均用） |
| intent 基准权重 | 0.6 | 乘以长度因子后使用 |
| context 基准权重 | 0.4 | 乘以长度因子后使用 |
| 长度因子范围 | 0.35～1.0 | 字数≥100→1.0，字数≤0→0.35 |
| eventStep 默认 | 20 | 触发 L2 抽取的楼层步长 |

## 五、降级策略

| 场景 | 降级行为 |
|------|---------|
| embedding API 未启用 | 召回返回空，prompt 不含 `<RecalledMemories>` / `<RecalledEvents>` |
| embed 调用失败/超时 | 捕获异常，`recalledMemories = []`，`recalledEvents = null`，正常发起请求 |
| reranker 调用失败/超时 | fallback 回 RRF 粗排顺序（`candidates.slice(0, topN)`） |
| fingerprint 不匹配 | 跳过该向量（模型切换后旧向量自动失效，不污染召回结果） |
| 缓存为空 | 直接返回空，不发起 embed 请求 |
| L2 召回/组装异常 | `recalledEvents = null`，L0 召回结果仍正常注入 |
| 摘要格式截断（parsed.summaries 为空） | 跳过 L0 embedding 写入，不污染索引 |

## 六、后续迭代：词法检索功能的落地方案

> 本章描述「词法第三路」的完整落地方案，作为当前稠密双路（dense-intent + dense-context）的补充通道。落地后整体召回变为 **3 路 RRF**，不改变任何已有机制，只在 `recallL2Events` 的现有 RRF 框架上追加词法分支。

### 6.1 为什么需要词法路

稠密检索（bge-m3 语义向量）的盲区是**生僻专名的精确召回**。「鹿茸酒」「破阵子」「唐沐梨」这类专名在 embedding 空间分布稀疏，同名词向量距离反而比同义语义词远；当用户输入只有人名时（2~3 字），`lengthFactor` 把 intent 路权重压至 ≈0.23，正确事件可能排不进 top-K。词法路直接做字符串匹配，无视向量空间密度，精确命中专名后以 RRF 名次拉高综合分，弥补这个盲区。

### 6.2 数据来源：`keywords` 字段

L2 事件抽取时（`runEventSum`），每条事件已包含 **`keywords`** 字段——3~6 个专名/物件/动作，与事件一并存入 `eventHistory`。词法检索以「**词 → 事件 id 集合**」倒排索引为核心数据结构：

```
"鹿茸酒" → ["evt-12", "evt-34"]
"萧白瑚" → ["evt-12", "evt-19", "evt-34"]
"探病"   → ["evt-12"]
"破阵子" → ["evt-07", "evt-22"]
```

> `npc` / `location` 字段的实体名**同样并入倒排**（与 `keywords` 合并去重），确保 NPC 名、地点名也参与词法检索，不遗漏实体硬匹配。

除倒排索引外，还维护一张**动态别名表** `_aliasMap`（alias → canonical NPC名），由 `eventMeta.aliases` 动态加载。别名**不入倒排索引**，只在查询侧归一化使用（见 6.5）。

### 6.3 倒排索引的构建与维护（`memory-recall.js`）

**运行期内存中的三张表**：

```js
var _invertedIndex  = new Map(); // Map<term, Set<eventId>>
var _termMatchFactor = new Map(); // Map<term, number>  原始=1.0 / 子串=0.5
var _docTerms       = new Map(); // Map<eventId, Set<term>>  用于精准删除
var _aliasMap       = new Map(); // Map<alias, canonical>  动态，从 eventMeta.aliases 加载
```

**触发时机与操作**：

| 时机 | 动作 |
|------|------|
| `addToCacheL2(rec)` | ① 将 `keywords ∪ npc ∪ [location]` 的每个**原始词** k 写入 `_invertedIndex`，`_termMatchFactor.set(k, 1.0)`；② **展开子串**写入 `_invertedIndex`：子串最小长度 = `ceil(k.length / 2)`（例如「苓雪妃」3 字 → 子串长度≥2；5 字词 → 子串长度≥3），只展开长度在 `[minSubLen, k.length-1]` 区间的连续子串，`_termMatchFactor.set(sub, 0.5)`（已以 1.0 存在则不降）；③ 在 `_docTerms.get(rec.id)` 记录所有入库 term（含子串）用于精准删除 |
| `removeFromCacheL2(id)` | 用 `_docTerms.get(id)` 取该记录全部 term，逐一从 `_invertedIndex[term]` 移除 id；空 Set 顺手删键 |
| 首次加载 `_cacheL2` | 遍历全量 `_cacheL2` 重建三张表（O(N·T)，T≈5，可接受） |
| `_syncL2EmbeddingsWithEventHistory()` 补缺/删孤后 | 分别调上面两个入口，索引随缓存自愈 |

**`_refreshAliasMap(eventMeta)`**：将 `eventMeta.aliases` 对象重建 `_aliasMap`，在以下时机调用：应用初始化完成、读存档/导入完成、每次 `applyMetaUpdates()` 执行后。

### 6.4 检索方向：关键词倒查原文（不对用户输入分词）

词法路的查询方向是：对**倒排索引中的每个 key**（事件关键词/NPC名/地点名及其展开子串），直接判断 `queryText.includes(key)`——而**不是**对用户输入切词再查表。

优点：
1. 索引键均为精确专名，不含虚词，无需停用词表。
2. 子串匹配自然支持：用户输入"鹿茹"时，倒排中就有以"鹿茹"为键的子串展开项，直接 `includes` 即可命中。
3. 性能可接受：倒排键总量 ≤1000（事件数 × 平均键数），每个 `includes` 在 ≤200 字 query 上耗时 μs 级。

**查询权重分配**：

| key 出现在 | `w_side` |
|------------|----------|
| intentText（用户当轮输入） | 1.5 |
| contextText（上轮 AI 回复） | 1.0 |
| 两侧都出现 | 取 max（1.5） |

### 6.5 词法打分：matchFactor 加权 IDF

每条候选事件的**词法分**：

$$\text{lexScore}(d) = \sum_{k \in \text{hits}(d)} w_{\text{side}}(k) \times \text{matchFactor}(k) \times \text{IDF}(k)$$

- $\text{matchFactor}$：1.0（原始精确匹配）/ 0.9（别名归一化命中）/ 0.5（子串展开项命中，子串长度 ≥ `ceil(原始词长/2)`）
- $\text{IDF}(k) = \log\!\left(\frac{N+1}{df(k)+1}\right)$，$N$ = 事件总数，$df(k)$ = `_invertedIndex.get(k).size`
- TF **不计**：`keywords` 已是去重词组，每个 term 不重复命中
- **同事件去重（防子串重复计分）**：`hits(d)` 按事件 d 为单位构建，而非直接对全量倒排键求和——按词长降序遍历该事件命中的所有 key，若某个**纯子串展开项**（非该事件的原始词）已被一个更长、已保留的命中词（原始词或另一子串）完整包含，则跳过其贡献；若该子串本身也是该事件的独立原始词，则不受影响、照常计分。例：事件同时命中「洞庭君」「洞庭」「庭君」，只按「洞庭君」一次计分，避免长关键词因展开出多个子串而被反复加权
- **别名扩展**：遍历完倒排后，额外扫 `_aliasMap`：alias 命中 intentText/contextText → 给 canonical 对应事件集追加 `w_side × 0.9 × IDF(canonical)` 分

### 6.6 三路 RRF 融合

三路 RRF 融合公式：

$$\text{rrfScore}(d) = \frac{w_{\text{intent}}}{K + r_{\text{intent}}} + \frac{w_{\text{context}}}{K + r_{\text{context}}} + \frac{w_{\text{lex}}}{K + r_{\text{lex}}}$$

- $w_{\text{intent}} = 0.6 \times \text{lengthFactor}(\text{intentLen})$
- $w_{\text{context}} = 0.4 \times \text{lengthFactor}(\text{contextLen})$
- $w_{\text{lex}} = \texttt{LEXICAL\_BASE} = 0.5$（**固定常数，不乘 lengthFactor**）

> `LEXICAL_BASE = 0.5` 的权衡：高于 context（0.4）表明精确专名命中比语义 context 路可靠；低于 intent（0.6）保证语义 intent 仍是主路；不乘 `lengthFactor` 是因为词法路的内部权重（intent 侧 ×1.5 / context 侧 ×1.0）已隐式处理了查询长度差异——短查询 term 少、命中集小，排名自然后移，外部再压是双重惩罚。

词法路未命中的事件 $r_{\text{lex}} = +\infty$，贡献为 0，实现时只对有命中的事件追加词法项即可。

### 6.7 词法旁路（Lexical Bypass）

词法排名进入「**全 L2 事件数前 20% 且不超过 `LEXICAL_BYPASS_CAP`（5）**」的事件（含并列）可完全**绕过向量相似度阈值和实体软过滤**，与向量阈值为「或」关系：

```
实际旁路数 = min(LEXICAL_BYPASS_CAP, ceil(_cacheL2.length × 0.20))
```

这防止事件极少时词法旁路把全部事件放行——例如 5 条事件时实际旁路数为 1，50 条时才到上限 5。

> **为什么不需要 dense gate**：本项目的 `rrfMap` 是**全量**的（`intentScored` 扫遍整个 `_cacheL2`，每条有向量的事件都进 `rrfMap`），`candidateLimit=5` 只在最后的 `scored` 循环截断输出。因此词法路要做的只是给已有条目**追加词法 RRF 分**，加分自然把命中事件拉高排名进入 top-5，不存在「截断窗口外需要打捞」的问题，不需要额外的 `LEXICAL_EVENT_DENSE_MIN`。纯关键词噪声（词法命中但语义无关且未入词法 top5）在最终 `MIN_SIM=0.60` 阈值处过滤。

### 6.8 集成到 `recallL2Events`（改动点）

在现有稠密 RRF 融合完成（`intentScored + contextScored → 全量 rrfMap`）之后、`list.sort()` 排序和 `scored` 截断循环之前，追加词法路分支：

```js
// ① 词法打分（关键词倒查原文，含别名贡献）
var _lexScores = _scoreLexical(opts.intentText || '', opts.contextText || '');
// _lexScores: Map<id, lexScore>

// ② 词法排名
var _lexRanked = Array.from(_lexScores.entries())
    .sort(function(a, b) { return b[1] - a[1]; });

// ③ 词法旁路集（与向量阈值是「或」关系，含并列）
var _lexBypassIds = new Set();
if (_lexRanked.length > 0) {
    var _bypassN = Math.min(LEXICAL_BYPASS_CAP,
                            Math.ceil(_cacheL2.length * 0.20));
    var _topNThreshold = _lexRanked[Math.min(_bypassN - 1,
                                  _lexRanked.length - 1)][1];
    for (var ti = 0; ti < _lexRanked.length; ti++) {
        if (_lexRanked[ti][1] >= _topNThreshold)
            _lexBypassIds.add(_lexRanked[ti][0]);
        else break; // 降序，可提前退出
    }
}

// ④ 给 rrfMap 中已有的命中事件追加词法 RRF 分
for (var li = 0; li < _lexRanked.length; li++) {
    var _lid = _lexRanked[li][0];
    if (rrfMap[_lid]) {
        rrfMap[_lid].rrfScore += LEXICAL_BASE / (RRF_K + li + 1);
    }
    // 不在 rrfMap 的 id（已被 excludeSet/指纹/无向量过滤）忽略
}
```

`scored` 截断循环同步扩展入选条件（原 simMax 阈值改为「或」关系）：

```js
for (var si = 0; si < list.length && scored.length < candidateLimit; si++) {
    var entry = list[si];
    // 词法高置信旁路（绕过向量阈值和实体过滤）
    if (_lexBypassIds.has(entry.id)) {
        scored.push(entry);
        continue;
    }
    // 向量相似度阈值
    var simMax = Math.max(entry.simIntent || 0, entry.simContext || 0);
    if (simMax < MIN_SIM) continue;
    // 实体软过滤
    if (!entityOk(entry, simMax, opts.focusCharacters)) continue;
    scored.push(entry);
}
```

### 6.11 参数定档

| 参数 | 值 | 说明 |
|------|-----|------|
| `LEXICAL_BASE` | **0.5** | 词法路 RRF 基准权重，不乘 `lengthFactor` |
| `LEXICAL_BYPASS_CAP` | **5** | 词法旁路上限；实际旁路数 = `min(5, ceil(全L2事件数 × 20%))`，含并列 |
| intent 侧查询权 `w_intent` | **1.5** | 索引键出现在 intentText 时使用 |
| context 侧查询权 `w_context` | **1.0** | 索引键出现在 contextText 时使用；两侧都出现取 max |
| `matchFactor`（精确） | **1.0** | 原始词直接命中 |
| `matchFactor`（别名） | **0.9** | 别名命中后解析为 canonical 匹配 |
| `matchFactor`（子串） | **0.5** | 索引键是原始词的子串展开项 |
| 子串展开最小长度 | **`ceil(原始词长度 / 2)`** | 按词长动态收紧，避免短子串噪声过多；例：3 字词 → 子串≥2 字；5 字词 → 子串≥3 字；2 字词 → `ceil(2/2)=1`，等于原始词长本身，不再展开子串（2 字词不细分） |
| IDF 公式 | `log((N+1)/(df+1))` | 标准平滑 IDF；子串展开键的 df = 其对应事件集大小 |
| 停用词表 | **不需要** | 检索方向为关键词倒查原文，索引键均为专名，不含虚词 |
| dense gate | **不设** | rrfMap 全量，无截断窗口；纯词法噪声由最终 `MIN_SIM=0.60` 过滤 |

# 姬侠传暗线/支线剧情系统设计方案书（V2 定稿）

> 调研基础：引擎流水线与存储层（Alex）、提示词与剧情链机制（Sam）、前端面板层（Tina）、战斗系统集成（Eric）四份带行号代码事实报告；两项用户决策已确认：**战斗节点走 iframe 回合制战斗**、**抉择节点铺垫一回合后弹出选项**。

## 一、目标与边界

### 1.1 功能目标
- 玩家在议事厅「打探传闻」→ AI 生成 3 条候选支线（名称/背景/总目标，玩家可见）；候选生成不限额，不满意可反复「换一批」，**接取时才占用每周 1 次的额度**。
- 接取后 AI 生成一棵**玩家不可见**的剧情树：普通阶段节点（隐藏目标+成功/失败判据）、**抉择节点**（显式选项按钮，玩家点击决定走向）、**战斗节点**（iframe 回合制战斗，胜负决定走向）、终点节点（多结局+奖励）。
- 每轮主对话后，后台异步判定普通阶段节点是否达成；抉择与战斗节点的走向由玩家操作/战斗结果**确定性**推进，不经判定 LLM。
- 抵达终点后仍须完成结局余韵，才正式结算奖励并关闭支线；开始支线后、余韵完成前确认返回门派，将由代码判定失败。节点判定失败/超时/战败仍按各自规则处理。
- 主对话 LLM 通过 msg4 注入的 `<SideQuestGuide>` 隐藏指导自然铺垫剧情，不向玩家暴露节点内容。

### 1.2 非目标
- 不做多支线并行（`maxActive = 1`）；不新增独立辅助模型配置（共用 `apiService.getConfig()`）；不把树转成 special-event 预写链；SillyTavern 环境整体静默跳过（`typeof pipeline === 'undefined'` 守卫）。

### 1.3 设计原则
- **零侵入持久化**：状态挂 `gameData.sideQuest`，`mergeWithDefaults/saveAppState/saveFullSnapshot/导入导出` 全自动兼容，storage-service 零改动。
- **注入负责铺垫，系统负责呈现**：选项按钮与战斗面板由系统在确定性时机渲染/触发，杜绝 LLM 自报事件导致的时序与映射失控。
- **主流程不阻塞**：LLM 调用全走 fire-and-forget Runner 范式（照抄 event-runner：`_running/_abortController/_failCount` 5 次熔断/5000ms 重试/cancel/resumeOnLoad）。
- **与剧本链互斥**：`currentSpecialEvent` 非空期间冻结支线（不注入/不判定/不计时）。

## 三、数据模型（`game-config.js` defaultGameData 新增）

```js
sideQuest: {
  active: null,            // 进行中支线（含玩家不可见的树）
  history: [],             // 已完结支线摘要，FIFO 上限 20
  lastRefreshWeek: 0,      // 最近一次接取/结算支线的记账周；候选生成不占次数，跨周结算占用结算周
  pendingReturnFailure: null, // 中途失败返程上下文；完整返程回复提交后清理，参与存档/重生成快照
  judgeDisabled: false     // 判定熔断开关
},
sideQuestConfig: {
  enabled: true,
  confidenceThreshold: 0.7,   // 判定置信度阈值（<阈值按 continue 处理）
  deadlineWeeks: 10           // 默认时限（周），0=不限
}
```

### 3.1 active 结构
```js
{
  questId: "sq_<ts>_<rand>", title, background, playerGoal,     // 后三项玩家可见
  acceptedWeek: 7, deadlineWeek: 17,
  relatedNpcs: ["E"], relatedLocations: ["沙州"], // 新支线唯一地点，统一门控212/213
  rootNodeId: "n1",
  nodes: { /* 3.2，玩家不可见 */ },
  currentNodeId: "n1",
  pendingInteraction: null | { kind: "choice"|"battle", nodeId, state: "buildup"|"awaiting" },
  turnsInNode: 0,
  log: [ { nodeId, result, reason, uiIndex, week, revealedTitle } ],
  progressNotes: "",        // 判定器逐轮累积证据摘要（≤300字），支持跨多轮目标
  status: "active", started: false, endingId: null, pendingEpilogue: false, // started 在抵达且同伴门控通过时设为 true
  lastJudgedUiIndex: -1     // 水位线：防重判/regenerate 后丢弃过期判定
}
```

### 3.2 节点 schema（统一结构，`type` 与 `interaction` 双轴）
```js
"n2": {
  type: "stage" | "ending",           // 原 branch（隐式推断）保留但非主力
  interaction: "none" | "choice" | "battle",
  title: "找到残卷的第一位经手人",     // 完成后向玩家回溯揭示
  hiddenGoal: "……", successCriteria: "……", failCriteria: "……",
  maxTurns: 0,                        // 超过→失败（0=不限）
  guideHint: "可让书肆老板无意提到……",

  // interaction === "choice"（显式抉择，玩家点击定走向，不经判定 LLM）
  options: [ { id:"b1", label:"交出残卷", narrative:"30-60字处境白描", next:"n4" }, ... ],

  // interaction === "battle"（iframe 回合制）
  battle: {
    enemyName: "独眼沙盗",            // 校验：禁与 15 个 commonNPCs 预设重名
    level: 4,                          // 0-9 → enemyWuxue → WUXUE_STAGE_DEFS 生成属性
    introText: "遭遇白描（玩家可见，作 currentBattleEvent.事件描述）",
    rewardGold: 200,                   // 即时赏金（按 level 参照悬赏公式预掷，211 固定写入）
    winNext: "n5", loseNext: "n6"      // loseNext 可指向失败结局或替代支路
  },

  // type === "ending"
  endingType: "success" | "bittersweet",
  epilogue: "结局摘要", 
  rewards: { "playerStats.声望": {add:8}, "npcFavorability.E": {add:5} }
}
```
全局失败惩罚固定 `playerStats.声望 -3`（service 写死，不交给 LLM）。

### 3.3 树结构硬约束（service 校验；每次接取只请求 1 次，失败不自动重试、不返还额度，由玩家手动重试）
- 节点规模按难度校验：简单 4–8（stage 2–5）、普通 6–10（stage 4–7）、困难 8–12（stage 6–9）；每树恰好 1 个 choice（2–3 个选项，每个选项须有唯一非空 `id`），简单/普通 0–1 个 battle、困难恰好 1 个 battle；ending 2–3 且至少 1 个 success。
- 所有 `onSuccess/options[].next/winNext/loseNext` 指向存在节点；root 可达全部节点；DFS 无环。
- `rewards` 白名单：`playerStats.{武学,学识,声望,金钱}`、`playerTalents.{根骨,悟性,心性,魅力}`、`npcFavorability.{A..O}`，运行时保留安全夹紧（属性≤3/声望≤15/金钱≤800/天赋≤3/好感≤10）；211 另按难度与预掷 enemy level 计算同等或更低的动态上限，简单禁天赋，普通天赋≤1，困难天赋≤2。规避历史上 `playerStats.魅力` 死键问题。
- `enemyName` 黑名单：战斗页 15 个 commonNPCs 预设名（重名会覆盖传入数值）。

### 3.4 持久化
挂 `gameData` 下自动纳入存档/快照/迁移，**零 storage 改动**。`candidates`（3 条传闻）仅存 runner 内存（仿 `_pendingBountyParams`）。支线完结仍写入 `sideQuest.history`；额外向 `eventHistoryService.appendEvents` 追加 `source:'sideQuest'` 结局事件的 L2 归档功能目前默认关闭，避免与 `runEventSum` 对支线过程楼层的总结重复。服务层保留 `ARCHIVE_SIDE_QUEST_TO_EVENT_HISTORY` 开关，置为 `true` 可恢复，既有 L2 记录不受开关影响。

## 四、提示词设计（4 份 txt → `PROMPT_SQ_*`，接入 promptOverrides + prompt-manager-modal 双预设分组）

### 4.1 `210支线-传闻生成.txt` → `PROMPT_SQ_RUMOR`
- **请求前预抽**：Runner 在每次传闻请求中抽选一次，并通过 `sqRumorThemes`、`sqRumorLocations`、`sqRumorNpcs` 传给 210 模板。八种题材为寻人、夺宝、恩怨、除害、秘闻、护送、比武、调解，每批无放回抽三种；三条传闻按数组顺序分别对应抽到的题材与地点。
- **地点池**：从 `getAccessibleLocations()` 返回的全部当前声望可达下山地点中抽三处，排除天山派，不限于示例中的四处。至少开放三处时批内不重复；仅开放一至两处时用开放地点补足三个位置；没有开放地点则不发请求。每条支线仍全程收束在其唯一地点，不跨地点旅行。传闻上下文中的 `sqLocationList` 同步为本批抽选地点。
- **NPC 池**：从 A–O 排除 L 的十四个编号中无放回抽三个，不受 `npcVisibility` 限制，不修改人物出场状态。210 只展示本批三个编号的既有人物简介；三个编号作为全批共同可选名单，不与传闻一一绑定，至少一条须牵涉本批 NPC。人物介绍沿用 010 的既有设定；211 的可见 NPC 素材规则保持不变。
- **事实与创作约束**：共享上下文提供年月周、季节、势力、最近三条剧情摘要及任务历史标题。事件基线只保留【世界事实基线】。每批至多一条直接承接近期剧情，其余独立取材，不违背已发生事实与人物状态，也不反复把同一性格标签作为事件起因。天山派说明改为“暗中组织义军，庇护流民”；另列西夏擒生军与吕氏伪军为敌人。保留本派弟子不得为反派的限制，删除指定友派为叛徒来源的要求。
- **换批记忆**：当前 `gameData` 会话内保留最近五批通过校验的候选摘要（标题、地点、背景、目标），不写入存档、世界事实或任务历史。失败请求不计入，读档/切换存档清空。旧候选仅作避重素材，不代表已经发生；回避核心起因、冲突、目标，不以改标题、地点或敌名冒充新题材。换批说明复用本次已经抽好的地点和 NPC，不再次随机抽取；允许复用地点或人物，但须换事件与诉求。
- **模板与返回校验**：默认 210 直接渲染预抽结果；旧自定义模板若缺少本批要求，Runner 在运行时追加，不覆盖用户保存的模板。地点先沿用现有合法性清理和前三条选择，再检查是否与本批对应顺序一致；NPC 必须在本批编号范围内。范围或地点顺序不符则整批失败并保留上一批候选，不强行改写模型字段、不自动重试、不消耗接取额度。
- 输出 `<SIDE_QUEST_RUMORS>{"rumors":[{title,background,playerGoal,relatedNpcs,relatedLocations,difficulty}]}</SIDE_QUEST_RUMORS>`。

### 4.2 `211支线-剧情树生成.txt` → `PROMPT_SQ_TREE`
- 输入：选中传闻及其唯一 `relatedLocations` + 时间/季节/主角所在地点 + 与 210 一致的已出场 NPC 详介（按可见性过滤并排除神秘杂役 L）+ commonNPCs 重名黑名单；当前游戏状态不注入主角属性概况，也不再注入全量合法地点池。全部节点必须在同一相关地点内完成，节点 schema 不再包含 `hardGates`。
- `buildTreeCtx()` 在服务层读取主角武学并折算境界，按难度预掷 enemy level：简单为玩家境界 `-2~-1`、普通相同、困难 `+1~+2`（均夹在 0–9）；战斗赏金沿用悬赏公式 `round((level+1)×500×[0.8,1.2])`。211 通过 EJS 接收固定的 `sqEnemyLevel/sqBattleRewardGold`，不让模型现场计算。
- 节点数、stage 数、战斗是否必需及各项结局奖励上限均由服务层按当前难度和预掷 level 计算，再通过 `sqNode*`、`sqStage*`、`sqBattleRequired`、`sqReward*` 等 EJS 变量直接写入硬约束；模板不按难度重复自然语言分档说明。结局天赋简单禁用、普通至多 1、困难至多 2，且仅 success 可给最多一项。
- 要求：阶段目标按白描五要素「谁/在哪/对谁/做什么/结果」具体可观察，禁"收集线索"式抽象目标；choice 选项须为道德/利益两难且各通向不同后续，`narrative` 古风白描第二人称；battle 的 `introText` 停在兵刃相向一刻，`enemyName` 有江湖气且避开黑名单，`loseNext` 尽量指向「败中求生」替代支路而非直接失败结局。输出 `<SIDE_QUEST_TREE>{…}</SIDE_QUEST_TREE>`。

### 4.3 `212支线-阶段判定.txt` → `PROMPT_SQ_JUDGE`
输入：近期剧情摘要（背景参考）置于前，随后依次是当前节点 hiddenGoal/successCriteria/failCriteria、progressNotes、本轮玩家输入与 mainText。原则：只依据正文实际发生之事、同义宽松匹配、未达成也未失败→continue。输出 `<SIDE_QUEST_CHECK>{"result":"continue|success|fail","confidence":0-1,"reason":"≤40字","progressNote":"≤60字"}</SIDE_QUEST_CHECK>`。`confidence < 阈值` 一律按 continue。**判定 LLM 只负责当前阶段的继续/成功/失败，不提供 branch/branchTo 跳线协议；choice 的分支由玩家选项决定，battle 的分支由战斗胜负决定，均不走判定 LLM。**

### 4.4 `213支线-阶段指导.txt` → `PROMPT_SQ_GUIDE`（主对话 msg4 注入，**五形态**）
各形态统一附 `active.background` 支线背景，让主笔在逐阶段推进时仍能把握整条支线前因。所有形态在渲染前均调用与 212 相同的 `checkStageGates()`：支线相关地点或随行 NPC 条件不满足时返回空字符串，prompt-builder 不注入指导及对应强调句。
| 形态 | 触发条件 | 指导要点 |
|---|---|---|
| stage 牵引 | `interaction:"none"` 普通节点 | 支线背景+隐藏目标牵引+铺垫建议 |
| choice 铺垫 | choice 节点 `buildup` | 支线背景+两难情境，停在决断点、勿替{{user}}决定 |
| choice 悬置 | choice 节点 `awaiting` | 支线背景+抉择悬置，玩家无关行动可自然呼应，仍勿代决 |
| battle 铺垫 | battle 节点 `buildup` | 支线背景+遭遇前 hiddenGoal/guideHint+introText；先完成铺垫，再停在交手前一刻 |
| ending 收束 | 终点节点 | 支线背景+结局走向，自然收束此线 |

三份调用类 prompt 均用 Runner 通用 6 消息越狱框架（system→user 素材引导→assistant 素材→user 任务→assistant prefill→user final）。override key：`SQ_RUMOR/SQ_TREE/SQ_JUDGE/SQ_GUIDE`。

## 五、引擎接入

### 5.1 prompt-builder.js
`buildMessages` ctx 新增 `sideQuestGuide = sideQuestService.buildGuideText()`；service 内统一检查 `enabled`、active/收束状态、剧本链互斥及 212/213 共用门控。`_buildMsg4User` 与 xiajin 预设 msg4 均在 `<MainTextGuidance>` 后新增 `<SideQuestGuide>` 块；计入 fixedTokens，自动挤压 PreviousMemories 预算。两套预设还在 `<user_input>` 强调句后按 `sideQuestGuide` 非空条件追加统一提醒：当前存在 `<SideQuestGuide>`，须与 `<user_input>` 一并遵循且不得向玩家泄露；无支线时不追加。

### 5.2 pipeline.js
`_commitResponse` 在 `eventRunner.maybeSchedule()` 后直接调用 `sideQuestRunner.afterCommit(parsed, sqMeta)`，主提交流程不等待其 LLM，但**自动存档必须等待返回 Promise 落定**。`SIDE_NOTE` 无效仍不自动存档；无 Runner、无支线、 awaiting 或冻结等快速返回路径仍可正常保存。

每轮提交生成自动存档 ticket，并在回调同时校验 ticket、`gameData` 对象引用和支线完成结果：新回合取代、读档/导入切换上下文、Runner 返回 `false`（取消/过期）均禁止旧任务写入。catch 回滚块调用 `sideQuestRunner.cancel()`；regenerate 快照包含 `gameData.sideQuest`，另有 `uiIndex ≤ lastJudgedUiIndex` 与 questId 双校验丢弃在途结果。

独立前端手动 `saveGame()`、JSON `_doExportSave()` 与 ST `_doExportSTJsonl()` 在创建 payload 前统一等待 `sideQuestRunner.whenSettled()`；等待期间若被取消或 `gameData` 已切换，则放弃本次保存并要求用户重新操作。文件名弹窗仍保持原同步调用顺序，兼容既有 UI 与测试入口。

### 5.3 side-quest-runner.js —— 判定主流程 `afterCommit(parsed, meta)`
完成语义：返回 Promise 只有在同步后处理、LLM 判定及全部重试结束后才落定；运行期间新到的轮次只保留最新排队项，每项有独立 Promise，被更新轮次取代时返回 `false`，首轮等待最新轮次实际补跑完成。`cancel()` 同时中止网络请求、重试等待和排队项，所有相关等待方收到 `false`。`whenSettled()` 跟随最新 `afterCommit`，供手动保存/导出使用；保存方不得用独立 `setTimeout` 绕过这条完成链。

前置过滤（任一命中即 return）：开关/无 active/状态非 active/熔断 → `currentSpecialEvent` 非空 → `pendingInteraction.state === 'awaiting'`（抉择/战斗等待期判定休眠，不计轮不计时） → `uiIndex ≤ lastJudgedUiIndex` → 同步时限检查（超 deadline → fail('超过时限')）→ 同步 maxTurns 检查 → `checkStageGates()` 不满足（turnsInNode++、更新水位线并 return，不调用 212 LLM）。该函数与 213 共用：`active.relatedLocations` 非空时必须包含 `mapLocation`，新支线由生成流程保证只有一个地点；`active.relatedNpcs` 为空时 NPC 条件放行，非空时则要求与 `companionNPC` 至少一个交集（中文名先归一化为字母 ID）。**旧节点 `hardGates`、`keywords` 字段仅作兼容保留，不再参与运行时控制；旧支线 `relatedLocations` 为空时不限地点。**

通过过滤后：
- **当前节点是 choice/battle 且 `state === 'buildup'`**：本轮正文已铺垫 → 转 `awaiting` 并呈现交互（见 5.4/5.5），toast「支线迎来关键抉择/狭路相逢」。
- **普通节点**：调 LLM 判定 → `extractXmlBlock('SIDE_QUEST_CHECK')` + `safeParseLLMJson` → `sideQuestService.applyJudgement`（回滚保护：应用前校验 uiIndex 水位与 questId 未变）：
  - continue：turnsInNode++，追加 progressNotes（截 300 字）；
  - success：log 揭示 title，`currentNodeId = onSuccess`，新节点若为 ending → 结算；若为 choice/battle → `pendingInteraction = {state:'buildup'}`；toast「支线有了新进展」；
  - fail：`status='failed'`，声望 -3，showModal 失败通告（reason 改写玩家口吻），入 history，active=null；支线结局 L2 归档开关默认关闭，不追加 eventHistory；
  - ending 两阶段结算：**抵达结局节点时**（`_settleEnding`，返回 `endingReached`，静默不弹窗）仅 `status='completed'`、`pendingEpilogue=true`、入 history；**收束轮正文写完余韵后**（`finalizeEpilogue`，置于 judgeDisabled 熔断之前）才 `applyRewards`（白名单+夹紧）、showModal（标题/结局/奖励）、清 active；支线结局 L2 归档开关默认关闭，不追加 eventHistory。
  - 每次应用后：`syncGameDataFromVariables → saveAppState → updateAllDisplays`。

### 5.4 抉择节点呈现（用户已确认：铺垫一回合后弹出）
进入 `awaiting` 时系统直接渲染：`game-ui.js` 新增 `displaySideQuestChoice(node)`，容器 `#sidequest-interaction-container`（置于 `#random-event-container` 旁、story-area 内），按钮复用 `.event-option-btn` 九宫格样式（label + narrative），与随机事件选项**分区共存**。awaiting 期间输入保持可用、按钮常驻、无超时。玩家点击后先重新执行 `checkStageGates()`，门控不满足时保留 `pendingInteraction` 且不推进，返回合法地点或恢复相关 NPC 随行后可继续；门控通过才同步推进 `currentNodeId = option.next`、揭示 title 入 log、清 pendingInteraction → 构造消息「第X年X月第X周【支线·标题】{{user}}下定决心：<label>」走 `handleMessageOutput` 正常入流水线（下一轮注入新节点指导）。

### 5.6 中途返回门派导致支线失败

- `worldmap-exit` 抵达支线地点、满足相关 NPC 随行条件后记录 `active.started=true`，随存档/快照保留。旧存档以当前门控、已有阶段进展或 `pendingEpilogue` 兼容；仅接取而未开始的任务不会因其他地点的普通返程被判失败。
- `returnFromSLG()` 在任何状态修改前弹出确认框，提示任务失败、声望 -3（最低 0）、无结局奖励。取消不改状态、不请求 LLM；确认绑定当时的存档、支线对象和地点，避免过期确认影响读档后的现场。
- 确认后取消旧判定，调用 `failQuestForReturn()`，确定性扣罚、占用结算周额度、记录失败并清 `active`。若已到 ending 但余韵未完成，则把该任务已有的 completed 历史改为 failed，不新增相反归档、不下发奖励。只有完整正文和有效 `SIDE_NOTE` 的余韵轮在门控通过后才正式结算。
- 返程清理支线抉择、待战卡、战斗预标记和输入锁，并按原返回流程重置 `GameMode/mapLocation/companionNPC/userLocation`。支线待战时仍可点击返回；正在生成、固定事件及实际战斗弹窗保持原锁定规则。
- `sideQuest.pendingReturnFailure` 保存原地点、实际同伴、目标、当前阶段和已发生的进展。专用 user input 描述主动放弃与返程；两套主笔预设使用失败 `<SideQuestGuide>`，屏蔽通用回山指导，夏瑾地点约束明确从原地点返回天山派。不得改写为成功、重复扣罚、发放结局奖励或重开任务；ending 阶段放弃时保留已发生的事实，只放弃未完成的收尾。
- 失败和返门状态在正文请求前保存到全量快照，重生成只重写返程剧情，不重复失败结算。完整回复提交后清理临时指导；网络错误、中断或格式不完整时保留以便重试，支线开关关闭也不能跳过已结算失败的收束。

#### 存档工况实测（2026-10-22，浏览器端到端 + 离线 vm）

发现并处治 3 处真实缺口（均已修复，`.scene3d-work/sq-save-load-verify.mjs` 8 场景全绿，离线 75 用例全绿）：

1. **battle awaiting 读档软卡**：三条显式读档路径（loadSaveSlot/ImportSave/loadSave 意图）及无 intent 刷新路径里，`resumeOnLoad()` 原先在事件恢复块**之前**执行，呈现的敌人卡片随后被 `hideBattleEvent()` 清掉、`inputEnable` 被 else 分支或 `parseLLMResponse` 无事件分支重置为 1 → 玩家可绕过战斗自由输入、支线判定休眠软卡。修复：4 处 `resumeOnLoad()` 统一下移到各自事件恢复/开场白解析完成之后。
2. **在途判定串台**：读档/导入/重生成的 runner 取消组原先漏了 sideQuestRunner——若取消瞬间判定在飞，结果可能写回新载入的存档（同 questId 旧档水位线兜不住）。4 处补 `sideQuestRunner.cancel()`。
3. **regenerate 残留战斗卡片**：battle awaiting 期间重生成按钮可用；快照回滚后 awaiting 消失，但 `updateStoryDisplay` 的 battle 显隐依赖内存态 `currentBattleEvent`，残留卡片可被重复挑战刷奖励。`_confirmRegenerate` 回滚后补清理（`hideBattleEvent()` + `currentBattleType=null`）。

既有行为备忘（非支线引入，不属本次修复范围）：无 intent 普通刷新会用硬编码开场白重跑 `applyParsedInit`，一切事件 UI（含普通随机/战斗事件）都被重置；事件框显隐遵循分页规则——读档恢复后正文停在第一页，翻到最后一页（事件描述页）事件框可见。

|---|---|
| 存档/读档（3 条路径 + 刷新） | sideQuest 全量随 gameData 恢复；choice/battle awaiting UI 重呈现、输入锁定正确（场景 A/B/C） |

#### 存档时序补强（2026-10-26）

## 九、关键决策记录
1. 支线走「自由叙事+隐藏指导+后台判定」而非 special-event 预写链：保 AI 自由度与玩家主导。
2. **抉择/战斗节点的走向由系统确定性推进（点击/战斗结果），不经判定 LLM**——解决 LLM 自报事件时序失控与选项-映射错位风险。
3. **战斗复用 turn-based-battle-new.html iframe + bounty 结算骨架**：敌参走 URL query（enemyName+enemyWuxue），新增 sidequest 结算分支；需同步修 startBattle 类型覆写与遮罩强退两处既有缺口。
4. 判定独立调用而非主回复 SIDE_NOTE 自报：避免主 prompt 复杂化与自评偏差。
5. 状态全挂 gameData：零迁移获得存档/快照/导入导出。
6. 节点失败即全线失败、所有终点即完成；放弃无惩罚、失败 -3 声望、战败走 loseNext（建树约束约半数为替代支路）。

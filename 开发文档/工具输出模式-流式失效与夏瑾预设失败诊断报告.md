# 工具输出模式：流式失效与夏瑾预设失败诊断报告

> 状态：诊断完成，尚未修改代码
> 涉及文件：`module/api-service.js`、`module/pipeline.js`、`module/prompt-builder.js`

---

## 一、问题现象

| 编号 | 预设 | 现象 |
|---|---|---|
| A | ny | 已开启流式。发送后界面一直停在「施延年铺纸研墨」，最后整段回复一次性出现 |
| B | 夏瑾 | 开启工具模式后发送失败。流式先报错，降级为非流式后再次报错，没有拿到任何回复 |

问题 B 的关键日志：

```
[API][DEBUG] 流式请求 body: {"model":"gemini-4-argon","temperature":0.9,"max_tokens":18000,"stream":true}
[Pipeline] 流式失败，尝试非流式降级: 工具输出模式：未返回预期的工具调用。
[API] 发送请求到 OpenAI: http://124.221.135.100:3000/v1/chat/completions
[API] OpenAI 响应, usage: {prompt_tokens: 49228, completion_tokens: 26, reasoning_tokens: 0, claude_cache_creation_*: 0, ...}
[Pipeline] API 请求失败: 工具输出模式：未返回预期的单次 submit_game_output 调用。
```

## 二、当前工具模式链路

1. `_wrapToolRequest`（`api-service.js` 第 133–158 行）先把原始 messages 用 `JSON.stringify` 塞进工具 `submit_game_output` 的 `description`。实际发出的只有一条很短的英文 user 指令，同时带上 `tools` 和 `tool_choice`（强制调用该函数）。
2. 流式请求进入 `_readToolStream`（第 249–358 行）：
   - 逐段读取 `delta.tool_calls[0].function.arguments`；
   - 用 `_createArgumentPreview` 把已经完整解码的 `display_stream` 字符增量交给 `onToken`；
   - 流结束时严格 `JSON.parse` 校验参数。
3. `pipeline.js` 的 `_requestWithStream`（第 693–770 行）：
   - 收到第一个 `onToken` 时切换为「伏案疾书」，之后每 1500ms 节流刷新一次正文；
   - 流式出现任何错误，都进入 `_fallbackNonStream`。
4. 非流式由 `_callOpenAI` 处理，再经 `_unwrapToolResponse`（第 182–207 行）解包。

界面状态与回调的对应关系：

| 状态文案 | 触发条件 |
|---|---|
| 铺纸研墨 | 请求开始 |
| 伏案疾书 | 第一次 `onToken`，即收到解包后的正文 |
| 蹙眉沉吟 | 第一次 `onThinking` |
| 题尾落款 | `onComplete` |
| 另起新卷 | 进入非流式降级 |

**推论**：如果长时间停在「铺纸研墨」，说明 `onToken` 一直没被调用，也就是前端一直没拿到可以显示的正文增量。这与正文里的 `<thinking>` 清理无关，因为状态切换发生在清理之前。

## 三、问题 A 诊断：ny 能拿到回复，但流式失效

流式开关本身是生效的：请求带了 `stream:true`，SSE 也正常结束。失效的是工具参数里的正文没有被增量交付。可能原因分三层。

### A1. 上游一次性返回完整参数（最可能，属于外部原因）

- 当前接口是 OpenAI 兼容的中转（new-api / one-api 一类，usage 里带有 `claude_cache_creation_*` 字段），模型是 Gemini。
- Gemini 的标准函数调用要等函数调用生成完毕，才一次性返回完整的 `args`。中转把它转换成 OpenAI 格式后，往往只有**一个 chunk**，里面就是全部 `arguments`。
- 这种情况下传输层确实是 SSE，但第一段增量就已经包含全部正文。客户端不可能提前显示还没收到的内容。

### A2. 客户端预览器的兼容性限制（客户端原因）

| 位置 | 问题 | 后果 |
|---|---|---|
| `api-service.js` 第 217 行 | 只认 `^\s*\{\s*"display_stream"\s*:\s*"` 这种开头 | 参数里还有其他字段且排在前面时，流结束前一个字都不显示 |
| `api-service.js` 第 320 行 | `if (name) emit(text)`：工具名还没到时，已解码的文字只缓存、不推出 | 工具名晚到时，要等下一个参数片段才释放；最坏一直等到结束 |

### A3. 界面节流间隔过长（加重因素）

- `pipeline.js` 第 729 行，节流间隔为 1500ms。
- 如果正文在最后短时间内集中到达，节流定时器还没触发就已经进入最终的 `renderMainText`，看起来就像整段出现。
- 这一条不能单独解释「长时间停在铺纸研墨」，只会加重整段出现的观感。

### A4. 原生 Gemini 分支（API 类型为 gemini 时）

- `_readToolStream` 的 Gemini 分支（第 289–294 行）按完整的 `functionCall.args` 处理，故意没有开启实验性的 `streamFunctionCallArguments`。
- 所以在这条路径下，工具模式必然是整段交付。

### 本地模拟验证结果

| 模拟返回方式 | 当前表现 |
|---|---|
| OpenAI 正常分片，`display_stream` 是第一个字段 | 正文多次增量更新 ✅ |
| 上游一次性返回完整参数 | 正文一次性出现 |
| `display_stream` 不是第一个字段 | 完成前没有任何预览 |
| 工具名最后才返回 | 可能一直等到完成才交付 |
| 原生 Gemini 完整 args | 正文一次性出现 |

## 四、问题 B 诊断：夏瑾预设没拿到回复

### B1. 直接原因：上游返回了普通文本，没有调用工具

- 流式阶段的报错「未返回预期的工具调用」来自 `api-service.js` 第 351 行，只有**整个流里一个 `tool_calls` 都没出现**时才会触发。
- 非流式重试时 `completion_tokens: 26`、`reasoning_tokens: 0`。也就是说，模型只回了大约 26 个 token 的普通文本就结束了。这类内容通常是确认语（「好的，我明白了……」）或简短的拒答。
- 两次报错文案不同，是因为它们来自两个检查点（流式第 351 行，非流式第 203–204 行），根本原因是同一个。

### B2. 为什么只有夏瑾触发（推断，需要诊断日志确认）

预设差异只体现在被塞进 `description` 的 JSON 里，外层的工具协议完全一样：

| 差异 | ny（6 条） | 夏瑾（4 条） |
|---|---|---|
| 消息结构 | system / user / assistant / user / assistant（预填充） / user | system / user / assistant / user |
| system 内容 | 常规设定 | `PROMPT_XJ_SYSTEM` **内嵌了假的 User/Assistant 对话** |
| 结尾引导 | 带 `<thinking>` 续写的预填充，「直接续写」的信号很强 | 结尾是很长的任务链和输出说明，信号相对弱 |

推断的机制：

1. **对话结构被压平**：原始消息变成 JSON 字符串放进 description 后，夏瑾 system 里那段假对话的样式更容易被模型模仿，于是模型用普通文本回一句确认语，而不去调用函数。
2. **强制调用可能没有生效**：中转把 OpenAI 的 `tool_choice: {type:"function", function:{name}}` 转成 Gemini 格式时，如果没有转成 `functionCallingConfig.mode = ANY`（变成了 `AUTO`），模型就可以选择不调用。这种情况下，ny 只是碰巧每次都调用了工具。

> 目前无法证实的原因：`_unwrapToolResponse` 和 `_readToolStream` 报错时没有保留 `finish_reason`、`message.content` 和 `tool_calls` 的摘要，看不到那 26 个 token 的内容。

### B3. 附带问题：协议错误也会触发降级重试，重复计费

- `pipeline.js` 第 754–765 行：流式出现**任何**错误都会进入 `_fallbackNonStream`。
- 降级请求**仍然使用工具模式**，把同一份约 4.9 万 token 的输入原样再发一次。
- 对于「没有调用工具」这类协议错误，重试几乎一定还会失败，白白多付一次费用。

## 五、修复方案

### P0：止损与诊断（建议立即实施）

| # | 修改 | 位置 | 说明 |
|---|---|---|---|
| 1 | 错误分类，协议错误不降级 | `api-service.js` 的 `_toolError` 增加 `err.code = 'TOOL_PROTOCOL'`；`pipeline.js` 的 `onError` 判断这个标记 | 没有工具调用、多个调用、参数无效、拒答、未正常完成等情况直接报错。只有拿到首字节前的网络错误或 5xx 才降级 |
| 2 | 解包失败时输出摘要 | `_unwrapToolResponse`、`_readToolStream` | 输出 `finish_reason`、`content` 前 200 字、`tool_calls` 数量和名称、`delta` 里出现过的字段集合。不输出密钥，正文要截断 |
| 3 | 流式时间线诊断 | `_readToolStream` 与 `_requestWithStream` | 记录首个 SSE、首个参数片段、首次解出正文、首次刷新界面、完成这几个时间点，以及参数片段数和总字节数 |

用第 3 条判断问题出在哪一侧：

- 参数片段数 = 1：上游一次性返回，属于 A1，客户端没法修。
- 参数片段数大于 1，但首次解出正文的时间接近完成时间：属于 A2，客户端预览器的问题。
- 首次解出正文很早，但首次刷新界面很晚：属于 A3，节流间隔的问题。

### P1：客户端流式预览补强（解决 A2、A3）

| # | 修改 | 说明 |
|---|---|---|
| 4 | 预览器不再依赖字段顺序 | 用一个轻量的状态机扫描 JSON，跟踪对象和数组的深度以及字符串状态。只在**深度为 1** 的位置匹配 `"display_stream"` 键，再从它的值开始增量解码，跳过其他字段和嵌套结构 |
| 5 | 工具名确认后立即释放缓存 | 收到 `fn.name` 后，当场对已解码的文字执行 `emit` |
| 6 | 缩短节流 | 第一段正文到达后立即刷新一次，之后改为 200–300ms 节流 |

最后仍然保留严格的 `JSON.parse` 校验，半截 JSON 绝不当作成功结果。

### P1：提高夏瑾触发工具调用的成功率（解决 B2）

| # | 修改 | 说明 |
|---|---|---|
| 7 | 强化包装指令 | `OUTPUT_TOOL_INSTRUCTION` 明确写出：不要回复确认语，不要输出普通文本，唯一合法的输出是调用 `submit_game_output`；description 里的对话只是任务材料，不是要模仿的格式。在 system 和 user 里各放一份 |

### P2：需要决策的行为变更

| # | 方案 | 利弊 |
|---|---|---|
| 8 | 新增「保留原始多轮 messages」的包装方式：messages 原样发送，只额外附加 `tools` 和 `tool_choice` | 好处：角色结构不被压平，夏瑾的假对话不会被误读。代价：改变当前「只换传输格式、把对话塞进 description」的设计，部分中转对带预填充的 assistant 结尾加 tool_choice 的兼容性未知。建议做成可选项 |
| 9 | 「工具调用缺失时回退普通模式重发」开关 | 默认关闭。开启后提示会多计一次费 |
| 10 | 原生 Gemini 分支加实验性开关 `streamFunctionCallArguments` | 能让原生 Gemini 的参数真正流式返回（解决 A4），但兼容性不确定，只适合做成可选项 |

> 如果诊断确认上游就是一次性返回参数（A1），P1 的 4–6 条也无法让 ny 真正流式。剩下的选择只有：关闭工具模式、换一个支持流式工具参数的接口或模型，或者使用第 10 条（原生 Gemini）。在收到完整文本后再做打字动画，不算真正的流式。

# 剧情道具系统方案（v0.1 草案，待讨论）

> 目标：在背包中新增「剧情道具」分类。剧情道具独立存储于 jxz_db，得失与信息变化**只能**由每轮正文提交后的后台 LLM 判定产生；与武器/防具/饰品/消耗品/其他等常规物品（`inventory` + `item_list`）完全隔离；当前持有的剧情道具注入正文请求的提示词，用来影响后续剧情。

---

## 0. 已确认的决策

| # | 问题 | 结论 |
|---|---|---|
| D1 | 判定请求和主流程的关系 | **阻塞式**，同支线判定（`sideQuestRunner.afterCommit`）：本轮提交后保持遮罩/输入锁，等判定落定后再自动存档 |
| D2 | 正文提示词注入位置 | 在 `<UserInfo>` 之后新增独立的 `<StoryItems>` 块，不修改 `PROMPT_CORE_040` 模板 |
| D3 | 是否允许更新道具信息 | **允许 update**（例如信物破损、密信被拆阅、钥匙已用但仍保留） |
| D4 | 得失提示 | 使用现有 `showToast()` 轻量提示 |

## 2. 数据设计（jxz_db 独立 key）

### 2.1 Key 一览

| Key（IDB） | localStorage 降级 key | 结构 | 说明 |
|---|---|---|---|
| `storyItems` | `jxz_storyItems` | `{ [itemId]: StoryItem }` | 道具**图鉴**：所有出现过的剧情道具（包括已失去、数量为 0 的），保存完整信息 |
| `storyItemHeld` | `jxz_storyItemHeld` | `{ [itemId]: number }` | 主角**当前持有**的数量，只记录 >0 的项 |
| `storyItemLog` | `jxz_storyItemLog` | `StoryItemLogEntry[]` | 得失/更新流水，FIFO 上限（建议 200 条） |
| `storyItemMeta` | `jxz_storyItemMeta` | `{ nextId, lastJudgedUiIndex, version }` | ID 计数器与判定水位线 |

> 为什么把“图鉴”和“持有”分开：
> 1. 失去后又重新得到同一件东西时（例如玉佩被抢走后又夺回），可以沿用原来的 `itemId` 和信息，不用重新生成；
> 2. 注入提示词和背包展示时只需要遍历 `storyItemHeld`，数据结构比较简单；
> 3. 以后要做“已失去道具”的回顾页也比较方便。
>
> **待讨论 Q1**：如果觉得 4 个 key 太多，可以把 `held` 合并进 `storyItems[id].count`，key 数减到 3 个。代价是查询“当前持有”时要过滤 `count>0`。

### 2.2 StoryItem 结构（LLM 生成 + 系统补充字段）

```jsonc
{
  "id": "si-12",                 // 系统分配，LLM 不生成
  "名称": "沈家玉佩",
  "类别": "信物",                 // 枚举：信物|文书|钥匙|秘籍残卷|宝物|证物|遗物|令牌|其他
  "描述": "羊脂白玉雕成的双鱼佩，背面阴刻一个「沈」字，边缘有一道旧裂纹。",   // 60 字内，客观外观
  "来历": "沈夫人临终前托付",       // 从谁/在哪里得到
  "剧情作用": "可作为沈家旧部辨认身份的凭证",   // 对剧情可能产生的影响，30 字内
  "关联人物": ["沈夫人"],
  "关联地点": "敦煌",
  "状态": "完好",                  // 自由短语：完好/破损/已拆阅/已使用/封印中…
  "属性": { "材质": "羊脂白玉", "铭文": "沈" },   // 自由 KV，存放其它特征
  // ---- 以下由系统写入 ----
  "firstGainedWeek": 37,
  "firstGainedUiIndex": 214,
  "updatedAt": 1730000000000
}
```

  "delta": 1, "countAfter": 1, "reason": "沈夫人临终托付", "at": 1730000000000 }

### 2.4 storage-service.js 改动（照抄 locationMemory）

1. 定义 `KEY_STORY_ITEMS / KEY_STORY_ITEM_HELD / KEY_STORY_ITEM_LOG / KEY_STORY_ITEM_META` 和对应的 `LS_*`；在 `_loadCacheFromLocalStorage` 中补上降级读取。
2. 读写接口一律用 `structuredClone` 深拷贝隔断引用（与 `saveLocationMemory` 的加固方式一致）：
   - `loadStoryItems()` / `saveStoryItems(obj)`
   - `loadStoryItemHeld()` / `saveStoryItemHeld(obj)`
   - `loadStoryItemLog()` / `saveStoryItemLog(arr)`
   - `loadStoryItemMeta()` / `saveStoryItemMeta(obj)`
   - `applyStoryItemChanges(changeSet)`：**一次性提交**图鉴 + 持有 + 日志 + 水位线四个 key，避免出现只写了一部分的中间状态
   - `clearStoryItemLayer()`：新游戏 / ST 导入时清空
3. **快照**：在 `_SNAPSHOT_KEYS`、`saveFullSnapshot()`、`restoreFromSnapshot()` 中加入 4 个 key，这样重生成/错误回滚时道具状态也会一起回退。
4. **存档**：`createSave()`、`buildSavePayload()`、`importSavePayload()`，以及 `index.html` 中 `loadSaveSlot` / `importSave` / 启动时 `loadSave` 分支（3 处 `saveLocationMemory(payload.locationMemory...)` 旁边）都要恢复。老存档没有这些字段时回退为空。
5. **新游戏 / ST 导入**：在 `clearLocationLayer()` 旁边调用 `clearStoryItemLayer()`（`index.html` 的 3756 和 5695 行附近）。

## 3. 判定 Runner：`module/story-item-runner.js`（新增）

### 3.1 触发与流程

```
pipeline._commitResponse
  ├─ appendUIConversation(assistant)          // 本轮正文已落盘
  ├─ eventRunner.maybeSchedule()              // 异步，不等待
  ├─ await Promise.all([                      // ← 改为并行等待，减少阻塞时间
  │     sideQuestRunner.afterCommit(parsed, sqMeta),
  │     storyItemRunner.afterCommit(parsed, siMeta)
  │  ])
  └─ autoSave()（两者都落定后才执行）
```

- **D1 阻塞式**：判定期间保持遮罩，`_setStreamLog` 显示状态文本（如「清点行囊」/「行囊清点完毕」）。
- **和支线判定并行**：两个请求互不依赖，用 `Promise.all` 并行等待，总耗时约等于两者中较慢的那个，不会叠加。
- `siMeta = { uiIndex, userMessage: preprocessed, week: currentWeek, onStatus: _setStreamLog }`。

### 3.2 前置过滤（不发请求、直接返回 true 的情况）

- 环境是 SillyTavern（`typeof pipeline === 'undefined'`）；
- `gameData.summaryConfig.storyItem.enabled === false`；
- `parsed.mainText` 为空，或 `parsed.sideNote === null`（回复被截断）；
- `uiIndex <= meta.lastJudgedUiIndex`（重复判定 / 过期轮次）。

### 3.3 输入素材（msg3 assistant）

```
【当前时间】第2年第10月第1周   【当前地点】敦煌
【主角当前持有的剧情道具】
<STORY_ITEMS_HELD>
[{"id":"si-3","名称":"天山令","数量":1,"类别":"令牌","状态":"完好","描述":"..."}, ...]
</STORY_ITEMS_HELD>
【主角曾持有、现已失去的剧情道具】（只列名称和 id，供“失而复得”时引用；建议最多 20 条）
si-7 半截断剑；si-9 沈家地契
【本轮玩家行动】{{userMessage}}
【本轮剧情正文】{{mainText（去掉段尾 |场景|时间|NPC|NSFW 标记）}}
```

> 补充：除了您提到的“正文 + 当前剧情道具”，我建议**再加上本轮玩家输入**。玩家输入可以帮助判断“送出 / 交还 / 收下”等意图，token 成本很低。另外，`mainText` 段尾的结构标记会干扰判断，喂给 LLM 前应先剥离。
>
> **补判（catch-up）**：如果上一轮判定失败（见 3.7），水位线不会前进。下一轮应把 `lastJudgedUiIndex` 之后、尚未判定的所有 assistant 楼层一起作为素材（上限 3 楼），漏掉的得失也能补回来。

### 3.4 System Prompt 要点（`STORY_ITEM_SYSTEM_PROMPT`）

1. **剧情道具的定义**（最重要）：对剧情走向有持续影响、具备唯一性或叙事意义的实物，例如信物、书信、地图、钥匙、令牌、秘籍残卷、证物、遗物、重要宝物。
2. **明确排除**：
   - 食物、酒水、药材、丹药、暗器补给等**消耗品**；
   - 金钱、普通货物、可在商店买卖的东西；
   - 武器、防具、饰品等**装备**（属于常规背包体系）；
   - 只是被看了一眼、被提到、没有被主角实际拿到手的东西；
   - 已经存在于【常规物品名单】中的名称（见 3.6 的隔离校验；也可以把 `item_list` 的名称做成短名单注入，**待讨论 Q2**）。
3. **得失判断标准**：只有正文**明确写出**主角拿到 / 交出 / 被夺走 / 损毁消失的结果才算；“打算送”“答应以后给”都不算。
4. **数量**：大多数剧情道具数量为 1；同名多件（如 3 枚令箭）才大于 1。失去数量不能超过当前持有量。
5. **update**：已持有道具的状态或信息因剧情发生变化时输出 update，只写变化的字段；不允许改 `名称`、`类别`。
6. **宁缺毋滥**：拿不准就不输出，绝大多数轮次应该是空变化。
7. 字符串中禁止使用英文双引号，引用一律用「」（沿用各 Runner 的统一规则）。

### 3.5 输出格式

```xml
<STORY_ITEM_CHECK>
{
  "analysis": "一句话说明本轮有无道具得失及依据（50 字内）",
  "gained": [
    { "ref": "new", "数量": 1, "reason": "沈夫人临终托付",
      "info": { "名称": "沈家玉佩", "类别": "信物", "描述": "...", "来历": "...", "剧情作用": "...",
                "关联人物": ["沈夫人"], "关联地点": "敦煌", "状态": "完好", "属性": { "材质": "羊脂白玉" } } },
    { "ref": "si-7", "数量": 1, "reason": "从马贼手中夺回" }
  ],
  "lost":    [ { "ref": "si-3", "数量": 1, "reason": "交还给呼延显" } ],
  "updated": [ { "ref": "si-9", "changes": { "状态": "已拆阅", "描述": "..." }, "reason": "主角拆开了密信" } ]
}
</STORY_ITEM_CHECK>
```

- `ref` 用系统 id 引用已有道具（包括已失去的），避免 LLM 用名称引用时出现别名、错字的问题。只有 `ref: "new"` 时才需要 `info`。
- 没有任何变化时输出三个空数组。

### 3.6 校验与落盘（纯代码，不信任 LLM）

| 校验 | 处理 |
|---|---|
| JSON 解析 | 复用 `_parseTaggedJson` 的四层容错（标签 → 去围栏 → 大括号切片 + 中文引号修复 → `safeParseLLMJson`）；建议把它提取成公共函数 |
| `gained.ref` 不存在 | 丢弃该条 |
| `new` 但名称和图鉴中某道具相同 | 视为对该 id 的 gain（去重），**不覆盖**原信息 |
| `new` 但名称命中 `item_list` | **丢弃**（隔离硬约束：常规物品不能变成剧情道具） |
| `new` 但类别不在枚举中 / 名称为空 / 名称超过 12 字 | 丢弃；类别非法时也可以兜底为“其他”（**待讨论 Q3**） |
| 数量非正整数 | 修正为 1；单条 gain 上限 5 |
| `lost` 的 ref 当前没有持有 | 丢弃 |
| `lost` 数量 > 持有量 | 截断为持有量；归零时从 `held` 删除（图鉴保留） |
| `updated` 的 ref 没有持有 | 丢弃（只更新持有中的道具） |
| `updated.changes` 包含 名称/类别/id/系统字段 | 剔除这些字段 |
| 单轮新增道具超过 3 个 | 只取前 3 个，并打印 warn（防止 LLM 把一堆杂物都当成剧情道具） |
| 落盘前过期检查 | `generation === _lifecycleGeneration` 且 `uiIndex > meta.lastJudgedUiIndex`，否则丢弃结果 |

落盘：调用 `storageService.applyStoryItemChanges(...)` 一次性写入四个 key，并把 `lastJudgedUiIndex` 更新为 `uiIndex`；然后用 toast 提示（D4）：

- `获得剧情道具「沈家玉佩」×1`
- `失去剧情道具「天山令」×1`
- `「密信」已拆阅`（update 默认只在状态字段变化时提示，避免刷屏）

### 3.7 失败与取消

- 同轮失败后间隔 1000ms 重试，最多重试 2 次（和支线判定一样，重试等待期间也响应 abort）。
- **重试用尽后的处理（待讨论 Q4，我的建议）**：和支线判定**不同**，不建议让整轮作废、要求玩家重生成。理由是剧情道具有补判机制（3.3），水位线不前进，下一轮会把本轮正文一起补判，所以：
  - 返回 `true`（允许自动存档）；
  - toast 提示「剧情道具判定失败，将在下一轮补判」；
  - 连续 5 轮失败时，调用 `autoDisableSummarySwitch('storyItem', ...)` 自动关闭开关（与其它后台任务的行为一致）。
- `cancel()`：`_lifecycleGeneration++` + `abort`。需要在现有调用 `sideQuestRunner.cancel()` 的所有位置加上一行：`_confirmRegenerate`、`loadSaveSlot`、`importSave`、`importSTSaveFromLoadModal`、pipeline 提交错误兜底（`index.html` 3287/3668/3785/4029/5468 行附近，以及 `pipeline.js` 1155 行）。
- `resumeOnLoad()`：阻塞式判定没有持久化队列，不需要恢复；补判机制会在下一轮自然覆盖漏判的楼层。

## 4. 正文提示词注入：`<StoryItems>`（D2）

在 `prompt-builder.js` 的 `_buildNpcUserBlock()` 中，`CORE_040`（`<UserInfo>`）之后追加：

```
<!-- <StoryItems> are plot-critical items currently carried by {{user}}. -->
<StoryItems>
以下是{{user}}当前随身携带的剧情道具。它们只能通过剧情获得或失去，不能买卖、丢弃或当作消耗品使用；在合适的时机自然地让它们影响剧情（被认出、被索要、成为线索或凭证等），不要每轮都刻意提及。
- 沈家玉佩 ×1【信物｜完好】羊脂白玉双鱼佩，背刻「沈」字。作用：沈家旧部辨认身份的凭证。
- 天山令 ×1【令牌｜完好】……
</StoryItems>
```

- 没有持有任何道具时**整个块不输出**。
- 每条只渲染 名称 / 数量 / 类别 / 状态 / 描述（截断到 40 字）/ 剧情作用，不渲染 `属性`、`来历`，控制 token 消耗。
- ny 和夏瑾两种预设都通过 `_buildHistorySummaryBlock(..., npcUserBlock)` 拼接，在 `_buildNpcUserBlock` 中改一处即可同时覆盖。
- 块头的说明文字用 `_po('STORY_ITEMS_HEADER', ...)` 包一层，可以在提示词管理里覆盖。

> **待讨论 Q5**：如果道具很多（比如超过 15 件），是否需要 token 上限或按“最近获得/最近变化”排序截断？建议先设一个 1500 token 的上限，超出部分只列名称。

## 5. 背包 UI（`inventory-panel.js` + `index.html`）

1. 在 `index.html` 的分类导航中、「其他」之后，新增 `<button data-inventory-category="剧情道具">剧情道具</button>`。
2. `render()` 按分类分两条路径：
   - 常规分类：保持不变（`inventory` + `item_list`）；
   - `剧情道具`：数据源是 `storageService.loadStoryItemHeld()` + `loadStoryItems()`，列表项按钮使用 `data-story-item="si-12"`，**不复用** `data-inventory-item`，避免误触发装备/使用逻辑。
3. 详情区展示：名称、持有数量、类别、状态、描述、来历、剧情作用、关联人物/地点、属性 KV（逐行显示）、获得时间（由 `firstGainedWeek` 换算成“第x年第x月第x周”）。
4. **不渲染任何操作按钮**；在详情区底部加一行灰色小字：「剧情道具，无法交易或丢弃」。
5. 空态文案：「暂无剧情道具 · 剧情中获得的重要物品会出现在这里」。
6. 隔离性检查：交易列表、装备栏、战斗道具、炼丹/种田同步都只读取 `inventory`，不需要改动。

> **待讨论 Q6**：要不要在剧情道具分类中加一个「已失去」的折叠区（从图鉴中读取 `held=0` 的道具）？实现成本很低，也能让玩家回顾剧情。

| 场景 | 行为 |
|---|---|
| 重生成本轮 | `saveFullSnapshot` 已包含 4 个 key → 回滚到发送前；`cancel()` 让飞行中的判定作废 |
| 判定进行中读档 / 导入 | `cancel()` + generation 校验，旧结果不写回新存档 |
| 特殊事件（`handleSpecialEvent` 也通过 `_commitResponse` 提交） | 正常判定；剧本正文中写到获得信物也会被识别，这是期望行为 |
| 战斗 / 随机事件选项结算 | 这些不通过正文提交，不判定；结算后的下一轮正文如果写到了就能判出来 |
| 回复被截断（`sideNote === null`） | 跳过，水位线不前进，由下一轮补判 |
| 玩家在自由行动里输入“我把玉佩扔了” | 玩家输入**不能直接**修改道具；只有当 LLM 正文写出扔掉的结果，并被判定为 lost 时才会生效（满足“得失只走 LLM 判断”）。是否需要在 `<StoryItems>` 中提示正文 LLM「剧情道具不可随意丢弃，应以剧情方式拒绝或婉转处理」？**待讨论 Q7** |
| ST（SillyTavern）环境 / `index - SR.html` | 整体跳过，不改动 |
| 老存档 | 4 个 key 缺失 → 空图鉴，水位线为 0；首次判定只看本轮正文（不回溯历史楼层） |

## 9. 待讨论问题汇总

- **Q1** 存储用 4 个 key（图鉴 / 持有 / 日志 / 元数据），还是把持有合并进图鉴改成 3 个 key？*建议 4 个。*
- **Q2** 判定 prompt 中是否注入常规物品名称短名单？`item_list` 有几百条，全量注入成本太高。*建议不注入，只靠代码硬校验丢弃同名项，prompt 中只用文字说明排除类别。*
- **Q3** 类别使用固定枚举还是允许自由填写？*建议固定枚举，非法时兜底为“其他”。*
- **Q4** 重试用尽后，是“允许自动存档 + 下一轮补判”，还是和支线一样“跳过自动存档并要求重生成”？*建议前者。*
- **Q5** `<StoryItems>` 的 token 上限和截断策略。*建议 1500 token，超出部分只列名称。*
- **Q6** 背包中是否显示“已失去”的折叠区？
- **Q7** 是否在 `<StoryItems>` 中约束正文 LLM：玩家试图丢弃或卖掉剧情道具时，应以剧情方式拒绝或婉转处理？
- **Q8** 开局是否需要预置剧情道具（例如按出身背景 A/B/C/D 给一件家传信物）？如果需要，就在新游戏初始化时写入图鉴和持有，不经过 LLM。这是否违反“得失只走 LLM 判断”的原则，需要您来定。
- **Q9** 特殊事件剧本（`special-event.js`）中写死的剧情物品，以后是否需要一个“剧本直接发放剧情道具”的确定性接口？这样不用依赖 LLM 识别，更可靠，但属于例外通道。

## 2. 当前实现

### 2.1 台词、声线与费用

游戏设置提供“语音配置”。玩家填写自己的Fish API Key，使用14个公开声线预设或自行修改绑定。整轮朗读默认关闭；单句测试有独立开关与明确合成按钮。

台词格式为`正文【稳定ID；简短表现描述】`，放在原五字段行的第一个字段末尾。例如：

```text
慢慢来。【D；轻声、稍慢】|山门|09:00|萧白瑚:平静|none
```

主回复同次给出归属，本地解析成具有UTF-16位置的台词单元。新对白每句独立一行，表现描述为1～24个Unicode码点。仅明确归属且已绑定的NPC口头对白进入合成；USER、NARRATOR、UNKNOWN分别保留玩家、旁白和不确定归属语义。声音表现与第四字段的立绘表情分别处理。

关闭配音时，主请求沿原流程发送。启用时只追加相应格式指令；上游工具输出封装、副API路由及原文本请求的失败处理继续保留。结束原因从实际响应透传，缺少完成依据时交由玩家处理。

提供商固定为Fish Drama 3，模型头为`drama-3`，发送文本为`[描述] 台词`，输出MP3。计费估算按实际UTF-8字节，包括表现指令。每轮24片段、3000字是工程限制，并非费用硬上限。语音失败由玩家选择重试、无声继续或暂停；缓存复用取决于正文、账号、声线、方向、路由等身份是否一致。

### 2.2 Web与Android传输

- **Web**：读取上游API配置中的跨域开关和地址，目标固定为Fish语音端点；使用独立Fish Key。一轮准备冻结路由，设置变化由指纹识别并要求明确处理。
- **Worker**：`worker/cors-proxy.js`增加`model`白名单，预检和转发一致；Fish路径保持音频流、拒绝重定向并返回安全错误。作者需同步实际部署版本。
- **Android**：复用CapacitorHttp适配能力，直接请求官方接口。当前原生通道支持JSON声线ID；网页支持的本地参考音频通过MessagePack发送，使用前校验平台能力。
- `apk/capacitor.config.json`关闭原生桥日志。原生请求等待上限180秒，停止结束本地等待，底层请求及计费仍可能继续；16MiB为JS逻辑检查，不是原生下载内存硬上限。

### 2.3 回合、待办与提交

整轮流程为：

```text
原动作/快照 → 主回复及台词标记 → 校验与声音准备
→ 原SIDE_NOTE/摘要/历史提交 → 上游支线afterCommit
→ 原回合完成回执 → 横屏演出
```

游戏通过`speechService`进入语音流程，`module/speech/runtime.js`协调准备并调用原commit；资源、奖励、事件和支线结算仍由原游戏持有。单句模式只记录可测试台词，用户确认后才生成声音。

待办保存在本机，可刷新后继续或无声发布。已成功片段可复用；已发布证据用于防止重复提交。`committing`结果不确定时保留核对状态，而不是自动重跑结算。

未发布待办存在时，新业务入口在扣资源前检查`speechService.guardProgress()`。原设置、只读面板及待办处理仍可访问；已经启动事务的结果归还和内部奖励/尾清理沿原流程执行。`pipeline.isBusy()`仍表示实际处理中状态。

### 2.4 演出、存储与恢复

完整回复进入横屏短段演出；中区完整返回原操作布局。原正文点击续读，原分页按有序原文定位，兼容重复文本。气泡和菜单借用同一输入节点、发送及重生成处理，原事件按钮仍执行原业务。

演出适配器复用上游GalParser、GAL控制器和3D渲染器，接管时持有自己的显示/幕布租约，退出归还原DOM、焦点、inert及独立锁。GM1保留原队列和逐帧时间规则；等待支线选择时沿原界面操作。

声音准备阶段确定文本切片；提交后采集最终阅读world，使SIDE_NOTE时间、季节、地点等与保存的阅读环境一致，同时保持音频片段身份。阅读、翻段和播放本身不执行剧情结算。

Key、参考和最近10轮录音存于独立本机语音库。普通存档保存正文、标记、阅读计划和游标，Fish凭证与音频不随普通存档导出。持久命名空间为`main`；epoch与gameData引用保护同正文读档等在途失效。页面有历史时恢复已存正文/事件，首次开局应用开场状态。

## 3. 文件职责与必须保持的接口

语音核心集中在`module/speech/`，共8个文件。游戏层只通过`speechService`调用核心能力；设置界面入口为`speechUI`，显示层回放入口为`speechPlaybackUI`。同目录内部对象用于各职责之间协作和白盒测试，不再分散接入游戏业务文件。

| 文件 | 职责 | 重点合同 |
|---|---|---|
| `service.js` | 对外入口、串行合成调度及缓存复用 | 预检、账号/路由身份、取消与晚到结果 |
| `runtime.js` | 持久待办、准备和原commit协调 | 待办阶段、进度指纹、一次提交、入口守卫 |
| `plan.js` | 单句解析与整轮切片 | 清洁投影、说话人、UTF-16范围、结束原因 |
| `provider.js` | Drama 3请求和Web/Android运输 | 固定模型、JSON/参考请求、平台能力与安全错误 |
| `msgpack.js` | 参考音频的二进制编码 | 字节一致性、类型与大小限制 |
| `config.js` | 声线预设、玩家配置及本地参考 | 保存归属、数据校验、已有绑定优先 |
| `store.js` | IndexedDB事务和10轮音频保留 | 归属/身份冲突、原子落库、明确字段保存 |
| `playback.js` | 单音轨播放器及已有录音解析 | 定位校验、停播、迟到保护、纯缓存回听 |

`ui/speech/settings.js`包含配置、单句测试和待办决策；`ui/speech/playback.js`负责原正文与演出段落的播放控件。对应样式分别是`settings.css`、`playback.css`。HTML按编码/提供商/计划/配置/存储/播放/回合/入口顺序加载核心，随后加载UI，继续采用普通脚本。

常用核心接口：`beginTurn`、`turnInstruction`、`setTurnCompletion`、`finishTurn`、`resumeTurn`、`releaseTurn`、`cancelTurn`、`loadPending`、`guardProgress`；配置与播放接口仍由同一个`speechService`提供。调用者的业务挂点保留在`pipeline/index`及原动作入口。

现行D3数据合同保留`jxz_speech_v1`数据库、`drama3-v1`声音版本、`inline-v1/round-v1`台词版本及`d3-m2a:/m3:`录音标识。文件组织不改变已有D3缓存身份。配置与回放按D3合同校验，未知版本报错并保留原记录；原游戏旧正文及存档读取规则继续沿用。

演出职责仍在`presentation-*`和`gal-scene-resources`，`media-context`提供活动游戏上下文。修改游戏挂点时同时核对上游afterCommit、读档与布局生命周期、提交回执及扣资源前守卫。

舞台只有一个渲染器：`galPresentation.renderLayers`（game-ui.js）同时服务竖屏演出与横屏阅卷，素材路径规则（场景图/立绘/CG/地点匾、季节昼夜、像素皮肤）全部收口在`gal-scene-resources.js`。竖屏按实时全局取世界状态并沿用站位记忆；阅卷把冻结的`presentationPlan.world`经`opts.context`传入、用帧上预算的`anchor`定位、`sceneTag:false`不画匾额、`missing`集合记忆缺图，图层挂在`#pr-stage`下再由`ui/presentation-reader.css`的ID作用域规则改成横屏样式。`clearLayers`只清传入容器的直系子层，原演出与阅卷互不穿透。改素材目录或图层结构只需动这两处，不要在阅卷里另起绘制代码。

协作者修改时应保持：

1. **一次结算**：准备成功不等于剧情已提交；未知提交不能通过重试按钮重放。原文本通道已有的网络回退也不能误称为“所有网络请求严格一次”。
2. **身份分层**：结构指纹、包含方向的声音指纹及最终阅读world各有用途。改变语气不能复用错误录音；更新阅读环境不应重新合成同一台词。
3. **上游时序**：生成、媒体准备、主提交、支线后处理和自动入场分别落定，不能仅在某个按钮上阻止提前进入。
4. **上下文保护**：读档、同正文替换、方向切换及晚到结果均按对应生命周期处理；不能用全局解锁代替归还自身租约。
5. **业务入口**：新增会变更进度的用户操作，在资源修改前接同步守卫；二级确认需复查。低层奖励函数和既有事务完成回调不应被当作新动作拦截。
6. **原界面所有权**：保持一份GalParser/GAL控制器，输入和事件采用原节点。幕布接口保留原四参语义，媒体owner使用附加参数。
7. **默认文字能力**：配音关闭或可选音库不可用时保留原文字路径；已知未处理待办的读取失败不能据此放行新剧情。

## 4. 建议的协作方式（待双方确认）

建议作者负责主仓玩法、UI方向及发布；语音模块维护方负责请求、编排、缓存和相关回归。演出CSS可由作者直接调整，行为改动需按上表联查。

- 先确认双方共同基线、实验分支和各自当前提交；交流使用commit ID及文件路径，不以截图或目录名称判断版本。
- 普通任务按文件组认领。`pipeline.js`、`index.html`、`game-ui.js`等共同文件在同一时间指定一个整合者；另一方先提交接口说明或独立补丁。
- 在实验分支做可评审的小范围功能批次，本地完成相关检查后统一提交。保持一份本报告的当前结论，不将全部内部工作记录带入分支。
- 作者主导视觉调整时，建议先确认布局/点击行为，再修改样式；语音侧随后检查原输入、菜单、事件和播放是否仍联动。
- 本轮按执行者本人进行定向快速测试，不再用子代理测试或重复运行无关全套。跨层改动或合并main前，再约定一次集中验收。
- 实验分支联调完成后，通过双方确认的PR/合并流程进入main；发布配置与账号由实际维护者操作。
